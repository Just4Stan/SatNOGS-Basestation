\section{RF PCB Design}
\label{sec:rf_pcb}

The RF PCB implements the front-end architecture responsible for signal transmission, reception, and communication with the host system. This section describes the electrical design of the PCB, including system architecture, component selection, and interconnections between subsystems.

\subsection{System Overview}
\label{subsec:rf_system_overview}

The RF PCB is based on a microcontroller-controlled dual-transceiver architecture supporting both the VHF (144\,MHz) and UHF (433\,MHz) frequency bands.

The design consists of the following functional blocks:

\begin{itemize}
\item A rp2040 based microcontroller for system control and data handling
\item Two RF transceivers (VHF and UHF)
\item Dedicated SPI communication interfaces
\item A UART interface to the Raspberry Pi host
\item Power distribution
\end{itemize}

Figure~X illustrates the high-level architecture of the RF PCB and the interaction between these subsystems.

\subsection{Microcontroller Subsystem}
\label{subsec:rf_microcontroller}

The RF PCB is controlled by a Raspberry Pi Pico microcontroller based on the RP2040. This device acts as the central control unit of the RF system.

Its responsibilities include:

\begin{itemize}
\item Configuration of both RF transceivers using SPI
\item Handling of transmit and receive data
\item Communication with the host system via UART
\item Control of auxiliary signals such as chip select and interrupt lines
\end{itemize}

The RP2040 was selected due to its dual-core architecture and availability of multiple independent SPI peripherals, enabling parallel communication with both RF transceivers without bus arbitration. Compared to typical single-SPI microcontrollers, this reduces firmware complexity and improves timing determinism.

Furthermore, the platform supports rapid firmware development and iteration through a well-established software ecosystem, enabling efficient testing and debugging during the development process.

\subsection{RF Transceiver Subsystem}
\label{subsec:rf_transceivers}

The RF PCB employs two CC1200 transceivers to enable dual-band operation. Each transceiver can operate independently and includes its own supporting circuitry:

\begin{itemize}
\item A 40,MHz crystal oscillator
\item External matching and filtering electronics
\item Decoupling capacitors for supply stabilization
\end{itemize}

The use of two dedicated transceivers eliminates the need for RF switching networks, simplifying the signal path and avoiding additional insertion losses.

Key control and interface signals include SPI communication lines, interrupt outputs (GDO pins), and device control signals such as reset.

This independent operation allows simultaneous configuration and rapid switching between frequency bands at the system level.

The detailed design of the RF front-end is discussed separately in Chapter~\ref{ch:rf-frontend}.

\subsection{Communication Interfaces}
\label{subsec:rf_interfaces}

\subsubsection{SPI Communication}
\label{subsubsec:rf_spi}

Each RF transceiver is connected to the microcontroller via a dedicated hardware SPI interface on the RP2040.

The SPI interfaces consist of the following signals:

\begin{itemize}
\item Serial clock (SCLK)
\item Master-out slave-in (MOSI)
\item Master-in slave-out (MISO)
\item Chip select (CS)
\end{itemize}

Interrupt lines from each transceiver are connected to the microcontroller to signal events such as packet reception or transmission completion.

Using separate SPI buses avoids contention and ensures deterministic communication timing.

\subsubsection{UART Interface to Host}
\label{subsubsec:rf_uart}

Communication between the RF PCB and the Raspberry Pi host is implemented via a UART interface.

This interface is used for:

\begin{itemize}
\item Transferring received RF data to the host
\item Receiving configuration and control commands
\item Debugging and diagnostic output
\end{itemize}

\subsection{Power Distribution Network}
\label{subsec:rf_power}

The RF PCB is powered from a 24\,V battery supplied via an XT30 connector. This input voltage is converted to a regulated 5\,V rail using a buck converter. The resulting 5\,V supply is used both to power the Raspberry Pi host through the board header and to supply the VSYS input of the Raspberry Pi Pico microcontroller.

Using a single 5\,V rail for both the host and the onboard controller simplifies the overall power architecture and reduces the required component count.

The Raspberry Pi Pico generates the required 3.3\,V rail using its onboard power supply circuitry, which is based on a switching regulator. This 3.3\,V supply powers both CC1200 transceivers as well as the associated digital circuitry on the RF PCB. While switching regulators typically introduce more noise compared to dedicated low-noise linear regulators, the integrated solution provides adequate current capability and efficiency for the system.

Given the noise sensitivity of RF circuits, particular attention was paid to supply integrity. Local decoupling capacitors were placed close to the supply pins of each active component to reduce high-frequency noise, provide transient current during switching events, and improve overall system stability. In addition, careful PCB layout practices were applied to minimize coupling of digital switching noise into the RF signal paths.

\subsubsection{Power Supply Noise Evaluation}
\label{subsubsec:rf_power_measurement}

Oscilloscope measurements were performed at the 3.3\,V pins of the CC1200 transceivers to assess voltage stability and switching noise characteristics. The measurements were conducted under multiple operating conditions, including idle, receive, and transmit modes.

The observed DC supply voltage was approximately \textbf{[X.XX\,V]}. The measured peak-to-peak ripple on the 3.3\,V rail was approximately \textbf{[XX\,mV\textsubscript{pp}]} under nominal operation, with transient deviations up to \textbf{[XX\,mV]} observed during mode transitions.

These results suggest that, despite the use of a switching regulator, the implemented power distribution network, in combination with local decoupling, provides adequate noise suppression for this prototype. For future iterations, the use of a dedicated low-noise LDO for the RF section may be considered to further improve supply integrity and RF performance.

\subsection{Summary}
\label{subsec:rf_summary}

The RF PCB electrical design integrates a microcontroller, dual RF transceivers, and dedicated communication interfaces into a modular and robust architecture. This design forms the foundation for the RF layout considerations discussed in the following chapter.

\section{Rotator PCB}
\label{sec:rotator_pcb}

The rotator PCB is responsible for controlling the azimuth and elevation motors and interfacing with the Raspberry Pi host system. In contrast to the RF PCB, which is primarily communication-oriented, the rotator PCB is centered around real-time motion control, motor driving, and position feedback acquisition.

The board integrates a Raspberry Pi Pico microcontroller, two dedicated motor driver ICs, encoder interfaces, end-stop inputs, and auxiliary communication peripherals. Together, these blocks form a compact control node for the antenna rotator subsystem.

\subsection{System Overview}
\label{subsec:rotator_system_overview}

The design consists of the following functional blocks:

\begin{itemize}
\item A Raspberry Pi Pico microcontroller for real-time control and communication
\item Two H-bridge motor drivers for the azimuth and elevation axis
\item Encoder inputs for both axes
\item End-stop inputs for mechanical limit detection
\item SPI output pads for connecting a IMU
\item A UART interface to the Raspberry Pi host
\item Auxiliary I\textsuperscript{2}C breakout connection for future expansion and debugging
\end{itemize}

Figure~X illustrates the high-level architecture of the rotator PCB and the interaction between the control, sensing, and actuation subsystems.

\subsection{Microcontroller Subsystem}
\label{subsec:rotator_microcontroller}

The rotator PCB is also controlled by a Raspberry Pi Pico microcontroller based on the RP2040. This device acts as the central control unit of the azimuth/elevation system.

Its primary responsibilities include:

\begin{itemize}
\item Producing PWM and direction control signals for both motor drivers
\item Reading encoder feedback from the azimuth and elevation axes
\item Monitoring end-stop signals
\item Handling fault and alert signals from the motor drivers
\item Communicating with the Raspberry Pi host via UART
\end{itemize}

The RP2040 was selected due to its flexible GPIO matrix, multiple hardware PWM outputs, interrupt-capable inputs, and sufficient processing resources for real-time motion control. 

The dual-core architecture also allows separation of time-critical motion-control tasks from host communication and supervisory logic, this reduces firmware complexity and improves responsiveness of the control loop.

\subsection{Motor Driver Subsystem}
\label{subsec:rotator_motor_driver}

The rotator PCB employs two TB6642FG motor driver ICs, one for each mechanical axis.

Each driver is configured as a single DC motor H-bridge which is powered directly from the 24\,V battery supply.

For each axis, the RP2040 controls the driver through three logic signals:

\begin{itemize}
\item PWM: regulates the effective motor voltage and therefore speed
\item IN1: enable/direction control input
\item IN2: phase/direction control input
\end{itemize}

This interface allows the microcontroller to control both motor speed and direction using a simple digital control scheme.

In addition to the control inputs, each TB6642FG exposes an ALERT signal connected to the RP2040. These fault outputs allow the microcontroller to detect driver-related abnormal conditions.

\subsection{Encoder and End-stop Interfaces}
\label{subsec:rotator_feedback}

Position feedback on the rotator PCB is done using a combination of encoder inputs, end-stop switches, and an auxiliary inertial measurement unit (IMU).

\subsubsection{Encoder Inputs}

Incremental encoder signals are used for both the azimuth and elevation axes. Each axis provides two channels A and B. These signals are connected directly to GPIO inputs on the RP2040, enabling quadrature decoding in firmware. This allows the microcontroller to determine both rotational position and direction of movement.

To improve signal integrity, each encoder channel is conditioned using a simple RC filter consisting of a 100\,Omega series resistor and a 100\,nF capacitor. This filtering reduces high-frequency noise and prevents false triggering.

\subsubsection{End-stop Detection}

Each axis includes a dedicated end-stop input for both azimuth and elevation. These signals are connected to GPIO inputs configured with pull-up resistors, allowing direct interfacing with mechanical limit switches. The end-stops provide a reference for homing procedures and prevent mechanical overtravel.

\subsubsection{Elevation Measurement using IMU}

In addition to encoder-based feedback, the elevation angle is measured using an external inertial measurement unit (IMU). This module provides tilt information, allowing direct estimation of the elevation angle relative to gravity.

The IMU is connected to the RP2040 via the available SPI interface, enabling periodic acquisition of orientation data. Compared to purely encoder-based methods, this approach allows absolute angle estimation without requiring a full homing sequence.

\subsubsection{Azimuth Reference via External System}

For azimuth referencing, the system leverages an external compass source provided through a web-based interface. This allows the system to obtain a global orientation reference without requiring additional onboard magnetic sensing hardware. The details of this interface are handled at the system level and are therefore not further elaborated in this section.

\subsection{Axis Connectors and External Interfaces}
\label{subsec:rotator_connectors}

The azimuth and elevation assemblies are connected through dedicated 6-pin JST connectors. Each of these connectors combines motor and encoder interfacing in a single cable harness. 

The connections include:

\begin{itemize}
\item Motor output +
\item Motor output -
\item Ground
\item 3.3\,V supply
\item Encoder channel A
\item Encoder channel B
\end{itemize}

Separate 2-pin connectors are provided for the azimuth and elevation end-stop switches.

Besides the actuator and sensor interfaces, the PCB also exposes additional test pads for I\textsuperscript{2}C1, SPI and uart. These pads improve accessibility during debugging and allow future system expansion without redesigning the core PCB.

\subsection{Communication Interfaces}
\label{subsec:rotator_interfaces}

\subsubsection{UART Interface to Host}
\label{subsubsec:rotator_uart}

Communication between the rotator PCB and the Raspberry Pi host is done via UART. This interface is used for receiving movement commands, reporting axis status and position and fiagnostics.

The UART operates at 3.3\,V logic levels and provides a simple and robust communication channel between the host and the local motor controller.

\subsection{Power Distribution and Design Iteration}
\label{subsec:rotator_power}

The rotator PCB is powered from a 24\,V input supplied via an XT30 connector. This 24\,V rail is used directly as the motor supply for both TB6642FG driver ICs.

This design includes an onboard buck converter, implemented using a TPS560430, to generate a regulated 5\,V rail. This 5\,V rail was connected to the RP2040 VSYS input and was intended to locally power the Raspberry Pi Pico from the main system supply.

In practice, however, this created an unintended power path through the Pico USB connection. Because the Pico was also connected by USB to the Raspberry Pi, the locally generated 5\,V rail could backfeed through the Pico USB port into the Raspberry Pi. To avoid this issue, the buck was removed from the pcb, and the Pico is instead powered directly by the Raspberry Pi over USB.

The Pico then generates the 3.3\,V rail using the onboard regulation circuitry and is used for the digital logic, encoder pull-ups, and external sensor interfacing.

\subsection{Summary}
\label{subsec:rotator_summary}

The rotator PCB electrical design integrates a Raspberry Pi Pico, two dedicated TB6642FG motor drivers, encoder and end-stop interfaces, and a UART host connection into a compact dual-axis control architecture. In contrast to the RF PCB, which is centered on high-speed communication with transceivers, the rotator PCB is structured around deterministic motor actuation and feedback acquisition.

By offloading low-level motion control to the RP2040, the design provides a modular and robust interface between the Raspberry Pi host and the mechanical rotator hardware, while also leaving room for future sensor and peripheral expansion.
